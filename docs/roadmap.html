This page is a snapshot; the other two are the authority

CLAUDE.md holds the constraints and outranks everything. The blueprint describes the architecture. This page describes only the remaining work, measured on 6 September 2026, and it goes stale the moment any of it is done — so treat a claim here as a lead to verify, not a fact to build on.

The unknown that dominated this project is gone

Until now every layer that touches a running game — the LCU client, the champ select socket, the live data poll, the suggestions, the matchup path — was unit-tested and had never met League. That was the single largest source of risk, and it has been discharged by playing a game. What replaced it is five ordinary bugs, which is a far better position.

01Five defects from the first real game

All five came out of one session against the real client. Four are traced to a specific line; the gold one has since been diagnosed from a captured game and its fix is fully specified. They are listed hardest-to-diagnose first, not most-severe first.

Defect 1

The gold number is wrong — fixed

Diagnosed from a captured game, 6 September. 81 samples across one 40-minute match, taken on the app’s own 30-second cadence. The earlier guess on this page — that consumables and trinkets were inflating the total — was wrong, and is recorded here rather than deleted because the way it was wrong is instructive. The captured game ended with no consumables in either inventory at all, so that theory could not have explained anything.

The live API’s price is the combine cost, not the item’s cost

It is exactly Data Dragon’s gold.base, never gold.total. Summing it counts only the last purchase in each item’s build path and silently discards every component already consumed into it.

Three readings from the capture settle it beyond argument, checked against Data Dragon 16.17.1:

ItemAPI pricegold.basegold.total
B. F. Sword — a base component130013001300
Blackfire Torch7007002800
Void Staff105010503000
Rabadon’s Deathcap110011003500
Chainlaced Crushers — finished boots001100

A base component reports its true cost, because for a base item the combine cost is the total — which is precisely why this survived review. Every completed item reports only its final step, and a finished pair of boots reports zero. A full six-item Viktor build summed to 3,950 gold.

What it did to the feature

46%Your spend was counted at 46% of its real value, averaged across the game.
37%The standing disagreed with the truth in 30 of 81 samples — behind, even or ahead was simply the wrong word.
18%You were genuinely behind and the app said nothing for 15 samples. Behind is the only footing that produces advice, so the check was silent in exactly the window it exists to serve.
16×It reported ahead when you were not in 16 samples — the reading that tells a player to keep doing what they are doing.

The error is biased, not noisy

It does not average out. A player holding raw components is counted near-correctly; a player who has finished their items is counted at a quarter of the truth. So the comparison systematically favours whoever has completed fewer items — which is usually the player who is behind. The check was not merely inaccurate, it was leaning the wrong way, and worst exactly when the gap was widest: 2,950 gold of error at 31 minutes.

The fix

The app needs gold.total per item, which the live payload never carries. data/meta/items.json already holds a committed cost field derived from Data Dragon — exactly the right shape and already compiled in with include_str! — but it covers only the 75 items in the defensive vocabulary, and none of the five above are among them. Widening that table to all 868 items is the whole fix, and it needs no new network call, no new dependency, and no change to how the tags already ship.

Done — and it uncovered a second bug on the way

The table now carries all 868 items at gold.total, regenerated by npm run meta:items. Pricing moved into recommend/state.rs, which is the only layer allowed to know what an item costs, and price is no longer read at all.

Wiring the table up immediately failed every lookup, which exposed something that had been latent for months: the payload field is itemID with both letters capitalised, and rename_all = "camelCase" renders it itemId, so item_id had been silently deserialising as zero the entire time. Nothing had ever read it, so nothing had ever noticed. It needed an explicit rename.

The scrubbed capture is committed at src-tauri/src/live/testdata/allgamedata.json and drives a regression test that asserts both the corrected verdict and the old one: the same payload reads ahead by 1,800 from the table and even by 800 from price. No hand-written fixture could have caught this, because the bug was in what a field means.

Two things still to settle. Sold and consumed purchases are still missing from any inventory sum, so “spent gold” remains an approximation even once the arithmetic is right — worth deciding whether the label should say so. And an item absent from the table must count as unknown rather than zero, or a future item will reintroduce this bug in miniature and just as quietly.

Why 219 passing tests never saw it

The stand-in client mints items as { itemID, price, count } with a price the test itself chooses, so every assertion agreed with an arithmetic that was never in question. The real payload carries nine fields per item — canUse, consumable, count, displayName, itemID, price, rawDescription, rawDisplayName, slot — and the bug lives entirely in what price means, which no fixture invented by the same person who wrote the parser could ever contradict. A captured payload is the only thing that could have caught this, and now there is one.

Defect 2

Opening the app mid-game detects nothing

The path exists and is deliberate. This is not a missing feature — it was built on purpose, with a comment saying so: opening the app after champ select is over is an ordinary way to use it, and the game names the same two things champ select does.

src-tauri/src/lib.rs:612 — “Opening the app after champ select is over is an ordinary way to use it, and until now it meant playing the whole game with no build on screen.”

The gate is probably not the problem. The live watcher sleeps on a watch channel that opens on any champ-select event other than ClientOffline, and ClientConnected is sent as soon as the socket connects — which happens mid-game, because the launcher stays running behind the game. That sequence looks correct on inspection.

src-tauri/src/lib.rs:489 — launcher_running.send(!matches!(&event, ClientOffline))
src-tauri/src/lcu/watcher.rs:156 — events.send(ChampSelectEvent::ClientConnected)

The strongest suspect is champion-key resolution. The two routes into a build resolve the champion differently, and only one of them can fail. Champ select receives the Data Dragon key from the client itself. The mid-game route has only the live API’s display name — Wukong, Cho'Gath — and converts it through champion_key_by_name, which reads the hand-authored tag file. A champion the tag file has never heard of yields champion_key: None, and no build at all.

src-tauri/src/lib.rs:350 — tags.champion_key_by_name(&player.champion_name)

A hand-authored judgement file should not gate a lookup

data/meta/champions.json exists to hold opinions — damage type, sustain, dive. Missing an entry there is supposed to cost you rule-based suggestions, and the blueprint is explicit that an untagged champion is a hole rather than a blank. On this route it costs the entire build instead, which turns a soft degradation into a hard failure. Data Dragon is already fetched and already maps names to keys; deriving it from there decouples the two regardless of whether it turns out to be the bug.

Three champions are untagged today — Locke, Yunara, Zaahen — and every future release joins them until somebody edits the file. That is enough to explain a reproducible failure on some champions but not a general one, so this needs confirming against the champion that was actually played.

Defect 3

The build never goes away after the match

This one is working as designed, and the design is wrong. The noGame branch deliberately leaves the build on screen, with a stated rationale.

src/main.ts:1272 — “The build in particular stays: the minutes after a game are exactly when someone reads what they should have built.”

The reasoning is sound and the result is still wrong, because the screen makes no distinction between a build for the game you are playing and a build for the game you just played. Those are the same pixels making two different claims, and the second one silently becomes a lie the moment the next champ select starts.

So the fix is not to clear it. Deleting the build would discard the exact case the comment is protecting. What is missing is a signal that the thing on screen is finished — a state on the header, the live pill reading something other than a live state, the standing banner retiring since it describes a game that has ended. Keep the build, mark it over.

Worth checking in the same pass: the BuildClaim that suppresses duplicate fetches is not released when a game ends, so whether the next game re-fetches correctly — particularly on the same champion — is unverified.

Defect 4

Situational shows several items and explains none of them

What is rendered. “Situational” arrives as several groups of one item each — a menu of alternatives — and is drawn as a row of tiles under a header that counts them. The header text is literally the count.

src/main.ts:547 — itemRowBlock(…)
src/main.ts:563 — const meta = single ? statLine(first.stats) : `${shown.length} options`

Each tile carries its own win rate in a tooltip, so the numbers are honest and per-item. What no tile carries is the only thing a player actually needs: when to buy that one rather than the one beside it. Six options with no discriminator is not six times as useful as one recommendation; it is roughly as useful as none.

The app already owns the missing sentences — a suggestion is { itemId, priority, reason, source }, and the recommendation engine produces exactly the reasoning that would disambiguate this row. It is rendered in separate blocks (“Against this team”, “For your team”) rather than against the items it is talking about.

The colour law makes this a design problem, not a text problem

The situational row is statistical — teal, drawn from the provider’s game counts. A reason is a rule — amber, and it argues in words. Dropping engine reasons into a teal block would let reasoning borrow a statistic’s authority, which is the precise failure the colour law exists to prevent, and painting the whole row amber would strip real win rates of theirs. Joining the two needs a rendering that keeps the sources visibly distinct, not a caption.

The cheaper half is available immediately and breaks no rule: the provider’s own numbers can order the row, and a group played in 3 games out of 98 probably should not sit beside one played in 40 as though the app were neutral between them. Saturation already encodes confidence elsewhere via railFor(); the same idea applies per tile.

Defect 5

Three empty slots on the rune page

They are not extra slots. They are the stat shards, and they are the best-understood defect on this page — two lines explain the whole thing.

No name. runeBlock passes undefined where every other tile passes a name, so tileLabel falls through to its last resort and prints the raw id.

src/main.ts:491 — tile(id, undefined, "tile sm", "perk")
src/main.ts:367 — name?.trim() ? … : `#${id}`

No art either. Icon art for a rune comes from icons.perks[id], which is built from Data Dragon’s runesReforged.json — and that file does not contain stat shards. The lookup misses, iconUrl returns null, and paintIcons returns early without ever inserting an image.

src/main.ts:311 — const path = icons.perks[key]; return path ? … : null

So each shard draws as a 24px box containing the literal text #5005 at 8px. Three of them, in a row, after the secondary runes — which reads exactly like three empty slots that should not be there.

The comment describes behaviour the code does not have

paintIcons is documented as leaving shards their text label permanently, and that is the right design — a tile with no art should fall back to words. But runeBlock never supplies the words, so the fallback lands one step further down on #<id>. The design was sound and the wiring was never finished.

The fix is a small table. There are nine stat shards in the game and their ids are stable: adaptive force, attack speed, ability haste, move speed, health, health scaling, tenacity, armour, magic resist. Data Dragon does not serve them and CLAUDE.md permits no third-party source, so a compiled-in table is the correct answer here — the same shape as data/meta/items.json, which is already committed rather than fetched. Nine rows removes the defect completely.

Worth fixing in the same pass: at 8px in a 24px box, a real name like “Adaptive Force” will not fit either. The redesign already raised item captions from 9px to 11px for exactly this reason, so the shard tile needs the same treatment or an abbreviation chosen deliberately rather than by slice(0, 9).

02The crawled data is not a dataset yet

The crawl works, has run against the live API, and has committed real output — the blueprint’s claim that this is untested is stale. What it has produced is not yet enough to stand behind. Measured directly over data/builds/:

A median of eight games behind the headline recommendation is far below the threshold this project already set for itself — the crawler’s own notes call a few dozen games per pair “below the threshold at which this app is willing to call a number a statistic”. RiotProvider can answer; it should not yet be the one answering.

The Riot key expires every 24 hours

The crawl runs on a development key, which Riot expires a day after issue. The daily schedule therefore fails every day after the key is rotated by hand — which is what the check-key gate exists to catch, and it will catch it loudly and then stop. Accumulation is the entire plan for this data, and accumulation is currently not happening unless somebody rotates a key each morning. Registering a personal or production key is the single highest-leverage item on this page.

It also changes the arithmetic rather than just the reliability. A production key raises the rate limit, and the rate limit is what shapes the whole crawler — the 45-minute clock, the decision to buy a timeline per match, the accumulate-don’t-replace design. With a patch cycle resetting the sample roughly every two weeks by design, the open question is whether the popular pairs reach significance before the reset and the rare ones ever do. Three honest answers exist: a better key, a narrower crawl that goes deep on fewer pairs, or accepting that OP.GG stays the live provider indefinitely and the crawl is a hedge rather than a migration. That decision has not been made and is worth making explicitly.

03Between a beta and something you hand a stranger

MissingItem set and rune page imports. Four buttons are permanently disabled, and the LCU client deliberately contains no code that could write. Needs the summoner id, a POST to /lol-item-sets/… and /lol-perks/v1/pages, and the button wiring. This is the only item on the page a user would call a missing feature.
MissingSelf-update. An installed copy cannot fetch a new version; every release is a manual download. Needs tauri-plugin-updater, a signing keypair and a manifest endpoint.
Half doneCode signing. macOS is already wired — adding the six APPLE_* secrets turns it on with no workflow edit, for $99/yr. Windows needs a certificate and has no equivalent shortcut. Until then both systems warn on first open.
MissingA settings UI. CLAUDE.md calls SPELLCHECK_LOCKFILE a user-facing setting on Windows, but the only ways to set it are an environment variable or a hand-edited providers.json in an OS config directory — which is exactly the population least equipped to do either.
MissingProvider fallback. If OP.GG is down or changes format the app has no answer, even though data/builds ships inside the bundle as a resource. The trait already makes this a small change.
MissingA version-agreement check. The tag must match three files and nothing verifies it; the README says so in prose. Ten lines of CI.
UnmeasuredMemory on Windows. The under-120 MB budget was set against WKWebView; Windows renders in WebView2, which runs more processes. CLAUDE.md forbids repeating the macOS number for Windows until somebody measures it, and nobody has.
UnprovenWindows on real hardware. It compiles in CI and produces an NSIS installer. No human has run it. The Mac cannot tell you otherwise — ring builds C, so there is no cross-compile.

04Named holes in the engine

Each of these is small, well understood, and already documented where it lives. None is urgent; all are cheap.

StaleThree untagged champions — Locke, Yunara, Zaahen. The tag file is pinned at patch 16.17.1 and every new release joins this list. See defect 2 for why this currently costs more than it should.
MissingTwo answers nothing can ask for. Shield reduction and crit reduction have items behind them but no champion tag that would trigger them, so Serpent’s Fang and Randuin’s Omen are never suggested. Closing this means adding a champion tag, not an item.
ThinCheck two emits one rule. Widening it requires adding an answers entry to data/meta/items.json first and a rule reaching for it second. The blueprint is emphatic that inventing advice to fill the space is the failure mode here.
FragileThe OP.GG vocabulary table. The two OP.GG tools disagree about champion names, and every new two-word-name champion needs a manual entry. The symptom is one champion failing while every other works — which is the hardest possible symptom to notice.

06What to do first

Ordered by what each step unblocks rather than by size.

  1. Rotate to a non-expiring Riot key. Minutes of work, and until it is done the data plan is not running at all. Everything in section 02 waits behind it.
  2. Widen data/meta/items.json to carry gold.total for every item. Done. All 868 items, pricing moved to the tag layer, a latent itemID deserialisation bug fixed on the way, and a real captured payload committed as the regression test.
  3. Re-point the stand-in client at the real payload shape. Done. scripts/fake-lcu.mjs now mints all nine fields with real ids and real combine costs, so a scenario can no longer invent a price the parser agrees with.
  4. Decouple mid-game champion resolution from the tag file. Correct regardless of whether it is defect 2’s cause, and it downgrades a class of hard failure to a soft one.
  5. Name the stat shards. Nine rows in a compiled-in table, and the only defect on this page whose fix is fully specified before anybody opens an editor. Do it while the rune code is already open.
  6. Mark a finished game as finished. Small, self-contained UI work, and it removes a screen that can silently assert something false.
  7. Sort the situational row by sample, then design the reason rendering. The first half is immediate and breaks no rule; the second half deserves thought, because the colour law constrains it.
  8. Get the Windows build onto real hardware and measure its memory. Two unknowns, one tester, one afternoon.
  9. Then imports. The largest genuinely missing feature, and the first thing on this list that is a project rather than a fix.

Imports stay user-initiated, however convenient automatic would be

When step 8 arrives: writing an item set or a rune page into the client is always a button press. Never automatic, never on a timer, never as a side effect of a lookup. The read-only LCU client is not an accident of scheduling — it is the rule expressed as an absence of code, and the first write path is where that rule stops enforcing itself.
