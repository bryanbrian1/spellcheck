00How to read this

The app marks every recommendation with a coloured rail down its left edge, and that rail carries meaning rather than decoration. This document uses the same three rails, for the same reason — by the time you reach the code you will already read them fluently.

Teal — how it is. A statement about the system as it currently stands, verified against the code.
Amber — a rule. A constraint that holds regardless of what seems convenient. Breaking one breaks something real.
Red — a gap. Does not exist yet. Expect nothing here to work.

CLAUDE.md outranks this page

The repository root holds CLAUDE.md, and it is the authority. This blueprint explains and connects those rules; where the two ever disagree, the file wins and this page is stale.

01The data path

One idea explains most of the architecture: every route to build data funnels through a single trait. Nothing above that line knows, or is allowed to discover, which source answered.

“No data” is an answer, not a failure

BuildLookup has two arms: Found and NoData. A source having nothing for Briar support is ordinary and gets rendered as a sentence. Err is reserved for things that actually went wrong — a dead endpoint, corrupt JSON. Conflating the two produces an app that cries wolf.

Validate champion keys before they touch anything

Champion keys become file paths and URL values. validate_champion_key in mod.rs accepts ASCII alphanumerics only — real keys look like Ahri, MonkeyKing, Kaisa, with no punctuation. It exists so ../../etc/passwd never reaches the filesystem. Route new sources through it.

03Adding a source

The trait is small on purpose — a label and one async lookup. Adding a third source touches three files and no schema, no UI.

  1. Create a module under build_data/ with a map.rs that turns the source's payload into a ChampionBuild, using the helpers in mapping.rs rather than hand-rolling field access.
  2. Implement BuildDataProvider for it — label() and fetch_build(). Return NoData when the source simply has nothing.
  3. Add a variant to ProviderKind and an arm to its instantiate match in config.rs. That match is the only place in the codebase allowed to name a concrete provider.

Which one is live is a config value, not a compile-time choice. providers.json in the OS config directory selects it, and LEAGUECHECKER_PROVIDER overrides that for development.

OP.GG data is borrowed, not ours

Query it per request and show it. Never write it into the repository and never redistribute it — that is republishing someone else's dataset. Only Riot-sourced data we crawl ourselves is distributable, which is the entire reason RiotProvider exists. The same rule covers the summoner-scouting tools on that endpoint.

Documented APIs only

Riot's official API, Data Dragon, and the OP.GG MCP endpoint. Never scrape a third-party site. And no Riot API key ever ships inside the binary — a key in a downloadable app is a key that gets extracted. Keys live in GitHub Actions secrets, where only the crawler sees them.

04The colour law

Teal means a statistic. Amber means a rule. This is the one piece of styling that is a correctness requirement rather than taste, and it is the easiest thing in the project to break by accident.

A teal block carries a win rate and a sample size, because it is describing what thousands of games did. An amber block carries a sentence explaining itself — “Aatrox and Soraka both heal, and nobody on your team has antiheal” — because it is reasoning, not measurement. A player must never mistake the second for the first.

Saturation encodes confidence. railFor() in main.ts reads the game count and dims the rail as the sample thins, so a build drawn from forty games cannot present itself with the authority of one drawn from eighteen thousand.

Amber never carries a number

If you find yourself putting a win rate in an amber block, the block is mislabelled — either it is actually statistical, or that number does not belong. A suggestion is { itemId, priority, reason, source } where source is "stat" or "rule", and the colour follows that field, never the designer's eye.

05The three checks

Designed, not built. Each check runs independently and returns zero or more suggestions.

1 · Enemy threat — what to build against

Reads the enemy composition's tags and answers them: the armour/magic-resist split, antiheal and when it needs to be online, tenacity, defensive actives.

2 · Team gaps — what to build for

Reads your own team's tags and finds the holes: no frontline, all-AD damage, nobody carrying antiheal, no engage.

3 · Game state — behind, even, or ahead

Compares you to your lane opponent using live game data. Behind, it favours components you can actually finish and waveclear over spikes you cannot afford; ahead, it pushes snowball items. This one only works in game — checks 1 and 2 run during champion select.

Both of the first two checks need tag files that describe champions and items: data/meta/champions.json for damage type, sustain, hard CC, dive, poke, frontline and engage, and data/meta/items.json for what each item answers, its cost, and what it builds into. Neither file exists yet.

06When work may happen

The binding constraint is not memory — it is CPU contention while the game is drawing frames. A helper app that stutters the game it is helping has failed, and low-end machines and Intel MacBooks feel it first.

Which leads to the rule that matters more than any individual optimisation: timing beats volume. During champion select, League is idle — you can make ten network calls and nobody notices. Mid-game, the same ten calls cost frames.

Do the expensive work in champion select

Fetch everything while the player is picking, hold it, then go quiet when the game starts. The in-game check has no event stream available and must be polled — so poll it slowly, or only when the player is dead or shopping. A one-second loop during gameplay is the most expensive mistake available in this codebase.

Two related consequences. The local RiotProvider is meaningfully cheaper than the live one — a file read against a TLS handshake — which is a real argument for migrating as our crawled data accumulates. And the window costs memory while it is open, so an app that hides itself once the game starts costs less than one idling behind the client.

07Talking to the client

The League launcher runs a small local web server so it can talk to itself, and it lets other programs listen. That is how champion and role arrive.

ThingValue
Lockfile/Applications/League of Legends.app/Contents/LoL/lockfile
FormatProcessName:PID:Port:Password:Protocol
AuthHTTP Basic, username riot, password from the lockfile
Base URLhttps://127.0.0.1:{port} — self-signed, so verification is disabled for localhost only
Subscribe[5, "OnJsonApiEvent_lol-champ-select_v1_session"]
ReadmyTeam[] → championId and assignedPosition

Roles arrive as top, jungle, middle, bottom, utility — support is utility. Role::parse already accepts this vocabulary, and fetch_build takes the raw string, so assignedPosition can be passed straight through with no translation layer.

Use the WebSocket. Never poll.

Connect to wss://127.0.0.1:{port} and subscribe. A polling loop wakes the CPU whether or not anything changed; the socket sleeps until the client speaks. This is the difference between fans spinning up and not.

League is usually closed

Not-running is the default state, not an edge case. Every code path that touches the client handles it, and the Search screen exists so the app is useful with no game open at all.

Imports are button presses

Writing an item set or a rune page into the client is always user-initiated. Never automatic, never on a timer, never as a side effect of a lookup. They currently ship disabled: the client layer reads, and has no code that could write.

08Built vs. not built

WorksBuild data layer. Two providers behind one trait, warning-free build. 86 passing tests across the crate.
WorksDesktop app. 420×700 window, dark UI, ~35 MB resident on a debug build.
WorksSearch screen. Type a champion, pick a role, see a build.
UntestedLive OP.GG requests. The plumbing compiles and every response shape is handled, but no request has ever actually reached the endpoint. If their payload differs from what map.rs expects, that surfaces on first use.
PreviewChamp select and in-game screens. Static sample data, labelled as such in the UI.
UntestedLCU layer. Lockfile, loopback HTTP client, champ select socket and the watcher over them, all unit-tested and wired through to build_for. No build of it has met a running League client yet, so the first real champ select is the test.
MissingChamp select in the UI. The Rust side emits lcu:status and lcu:build; nothing in main.ts listens to either yet, so the screen is still the static preview.
MissingRecommendation engine. All three checks, plus both tag files.
MissingCrawler and CI. data/builds/ is empty, so RiotProvider has nothing to read.
MissingMatchup builds. The design promises “core build vs. Syndra”, but BuildRequest carries champion and role with no opponent field. Needs a schema change and provider support on both sides.

09Build and run

Rust was installed with --no-modify-path, so cargo is not on the default PATH until you add it.

# once, if `cargo` is not found
echo '. "$HOME/.cargo/env"' >> ~/.zshrc

# run it
npm install
npm run dev

# ship it — .app lands in src-tauri/target/release/bundle/macos/
npm run app

# tests
cd src-tauri && cargo test

There is no bundler. tsc emits dist/, the HTML and CSS are copied beside it, and withGlobalTauri means the page needs no npm package at runtime. TypeScript and the Tauri CLI are the only frontend dependencies, both build-time.

Explain a dependency before adding it

The app renders in the system WebView, which is what keeps it small — an Electron shell would blow the memory target on its own. No React, no Tailwind, no component library, and no crate that isn't earning its place. If it isn't strictly necessary, it doesn't go in.

10Where to start

Cheapest first: make one live request

Open the app, type Ahri. Either a build appears or a clear error does, and either way you have learned whether opgg/map.rs matches the real payload. Everything downstream rests on the answer, and it takes about two seconds.

Biggest payoff: listen to the champ select events

The LCU layer already emits lcu:status and lcu:build from Rust, and the champ select screen already knows how to render a build — it is drawing sample data. Wiring the second to the first is what turns “type a champion name” into the product, and it is the change that first puts the whole path in front of a real client.

Safest place to learn the codebase: the tag files

data/meta/champions.json and data/meta/items.json are pure data with no plumbing. Writing them teaches you the domain the engine reasons about, and nothing breaks if you get an entry wrong.

Whatever you pick: small commits, and a message body explaining why the change happened rather than restating the diff. The git log is the reasoning record for everyone who comes after you.
